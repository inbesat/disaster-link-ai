[Slide 1] When the Ganga floods in Bihar, the cell towers go down first. Most disaster apps die with the network — leaving citizens without warnings and responders without data. That is the problem we walked into.

[Slide 2] SafeSphere is built for that exact moment. It is a dual-mode platform from a single codebase: citizens get a one-tap emergency companion app, while government responders get a full Emergency Operations Center with live metrics, geospatial intelligence, and multi-channel alerting. Two doors, same data, completel dvfjbjvdlvk cbscjkkvdvjdjky different experiences.

[Slide 3] When the internet dies, alerts cascade through nine redundant channels — SMS, web push, email, WhatsApp, in-app, and critically, FM radio broadcasts via CAP v1.2 XML with AI-generated voice in Hindi and English. That reaches feature-phone users in their own language within eight seconds. No other platform in this hackathon does radio.

[Slide 4] The AI does not just predict floods. It plans forty-eight-hour evacuations using a LangGraph multi-agent pipeline — predictor, planner, allocator, validator, communicator — grounded in real NDMA guidelines through a RAG pipeline over pgvector embeddings. The planner outputs concrete routes, shelter assignments, and resource deployments, not just text.

[Slide 5] And the whole system works offline: a forty-eight-hour IndexedDB cache for predictions, shelters, and alerts; a local Gemma two-B model that runs in the browser via WebLLM; and a sixty-one-rule static fallback that never goes silent, even on a dead device with no cache. The AI never hallucinates an evacuation order because the critical path is rule-based.

[Slide 6] Predict. Plan. Alert. Evacuate. Verify. One platform from river gauge to field responder. That is SafeSphere.

Anticipated Q&A — honest answers for technical judges

Q1: "Are these really five AI agents?"

  • A: No — they're deterministic LangGraph pipeline nodes (predictor → planner → allocator → validator → communicator) that use keyword/feature matching. Only the conversational chat uses an LLM. Critical decisions cannot be hallucinated because they're rule-based. lib/agents/graph.ts

    • Q2: "Is your ML model really predicting live, or is that a mock?"

  • A: The XGBoost model with four features (72h rainfall, river trend, soil saturation, elevation) is real and served via FastAPI. However, the trained artifact flood_xgboost_model.pkl is currently missing from ml_models/ — the service falls back to a mock label. We are transparent about this: on stage we say "fallback label" not "live prediction." ml_service/api.py

    • Q3: "What happens if all your API keys are removed right now?"

  • A: The alerting and broadcast path (CAP v1.2, SMS, Push, FM) never touches an LLM — it's fully deterministic. The conversational chat falls through: Groq → OpenRouter → Bluesminds → WebLLM (Gemma-2B in browser) → 61-rule static fallback. The rule-based fallback has 50+ disaster scenarios and never goes silent. RAG degrades to keyword search if OpenAI key is missing. lib/ai/openrouter.ts lib/ai-bridge/rule-based-fallback.ts

    • Q4: "How does offline actually work — is it simulated?"

  • A: Real implementation. Dexie wraps IndexedDB for predictions, alerts, shelters, resources, and pending reports. A custom service worker (Workbox) precaches the app shell, runtime-caches API responses network-first, and registers periodic background sync. Push notifications queue in Cache API and replay on reconnect. The local Gemma-2B model downloads to IndexedDB via WebLLM. lib/offline-sync/ worker/index.js lib/ai-bridge/webllm-provider.ts

    • Q5: "You claim 9 alert channels — which are actually live?"

  • A: SMS (Twilio), Web Push (VAPID), Email (Nodemailer), FM Radio (5 strategies: CAP API, RDS, FTP, Email-to-studio, IVR), In-App (Novu-ready), WhatsApp (webhook stub). All fan out in parallel from the alert engine. Twilio is bypassed in demo mode. FM strategies are implemented but need station APIs for end-to-end. lib/broadcast/fm-dispatcher.ts lib/sms/

    • Q6: "Is the RAG really using NDMA documents?"

  • A: The pipeline exists: PDF upload → text extraction → chunking → OpenAI embeddings (1536-dim) → pgvector HNSW index → cosine similarity search → context injection. If OPENAI_API_KEY is missing, it silently falls back to keyword search over stored chunks — no errors, no empty results. Demo uses seeded NDMA guideline chunks. lib/rag/

    • Q7: "How do you prevent a citizen from accessing the gov dashboard?"

  • A: Middleware enforces dual-mode crossover guards: a role=public cookie blocks /gov/* routes (redirects to /public/dashboard); a gov role blocks /public/* unless view_as_public is set. Admin routes require super_admin or district_admin — guests are bounced to 403. middleware.ts

    • Q8: "What's the story with all those env vars in .env.example — GLOFAS, NASA, Sentinel?"

  • A: Of ~40 env vars, only ~20 are wired into real code paths (Supabase, OpenWeatherMap, Groq/OpenRouter/Bluesminds, Twilio, VAPID, TTS providers). GLOFAS, NASA, Sentinel Hub, FIRMS, IMD, CWC, data.gov.in, GraphHopper, Novu, HDX are declared but not called anywhere. We do not claim live integration with them. .env.example

    • Q9: "Can this scale beyond Patna?"

  • A: Yes. The architecture is district-agnostic: PostGIS geospatial queries, pgvector RAG, CAP v1.2 radio, Dexie offline, LangGraph planning — all parameterized by district. Deploy to another district by seeding shelters, resources, FM stations, and alert rules. The middleware's district scoping and RLS policies handle isolation. prisma/schema.prisma lib/broadcast/auto-trigger.ts

    • Q10: "What's the biggest technical risk you're carrying?"

  • A: The ML model artifact is not checked in — the FastAPI service will fail to load it and return a mock label until train_model.py runs against historical_flood_data.csv. Also, the 6 MB JS chunk may slow cold start on stage Wi-Fi. Both are fixable before demo. ml_models/ next.config.mjs
