Arnav ~280 words / ~2:10

When the Ganga floods in Bihar, the cell towers go down first. In the last major flood, over 60% of rural districts lost mobile connectivity within the first six hours. That means the very people who need warnings the most — farmers in low-lying villages, families in feature-phone households, elderly citizens who don't use smartphones — are the ones who get left in the dark. Most disaster apps in the market today assume you have a smartphone and a 4G connection. They show you a risk score on a map and call it a day. But when the network dies, that map is useless.

SafeSphere is built for that exact moment. We asked a simple question: what if a village with zero internet could have the same intelligence as a district control room? Our answer is a dual-mode platform from a single codebase. Citizens get a one-tap emergency companion app — risk level, nearest shelter, SOS button, family safety status. Government responders get a full Emergency Operations Center — live metrics, geospatial intelligence, AI-powered evacuation planning, multi-channel alerting, resource dispatch. Same database, same APIs, completely different experiences enforced by middleware, server actions, and PostgreSQL Row-Level Security. A citizen in Patna and a DDMA officer in the same building use the same platform but see entirely different tools.

What makes us different — our five USPs — is that we don't just predict floods. We plan evacuations using a LangGraph multi-agent pipeline that outputs structured 48-hour plans with specific villages, routes, shelter assignments, and resource deployments. We reach people with zero internet through nine redundant alert channels including FM radio via CAP v1.2 XML with AI-generated Hindi voice — reaching feature phones and car radios within eight seconds. Our AI recommendations are grounded in real NDMA guidelines through a RAG pipeline over pgvector, not hallucinated platitudes. And the entire system works offline: 48-hour IndexedDB cache, local Gemma model in the browser via WebLLM, and a 61-rule fallback that never goes silent. Predict. Plan. Alert. Evacuate. Verify. One platform from river gauge to field responder.

Anticipated Q&A — honest answers for technical judges

Q1: "Are these really five AI agents?"

A: No — they're deterministic LangGraph pipeline nodes (predictor → planner → allocator → validator → communicator) that use keyword/feature matching. Only the conversational chat uses an LLM. Critical decisions cannot be hallucinated because they're rule-based. lib/agents/graph.ts

Q2: "Is your ML model really predicting live, or is that a mock?"

A: The XGBoost model with four features (72h rainfall, river trend, soil saturation, elevation) is real and served via FastAPI. However, the trained artifact flood_xgboost_model.pkl is currently missing from ml_models/ — the service falls back to a mock label. We are transparent: on stage we say "fallback label" not "live prediction." ml_service/api.py

Q3: "What happens if all your API keys are removed right now?"

A: The alerting and broadcast path (CAP v1.2, SMS, Push, FM) never touches an LLM — it's fully deterministic. The conversational chat falls through: Groq → OpenRouter → Bluesminds → WebLLM (Gemma-2B in browser) → 61-rule static fallback. The rule-based fallback has 50+ disaster scenarios and never goes silent. RAG degrades to keyword search if OpenAI key is missing. lib/ai/openrouter.ts lib/ai-bridge/rule-based-fallback.ts

Q4: "How does offline actually work — is it simulated?"

A: Real implementation. Dexie wraps IndexedDB for predictions, alerts, shelters, resources, and pending reports. A custom Service Worker (Workbox) precaches the app shell, runtime-caches API responses network-first, and registers periodic background sync. Push notifications queue in Cache API and replay on reconnect. The local Gemma-2B model downloads to IndexedDB via WebLLM. lib/offline-sync/ worker/index.js lib/ai-bridge/webllm-provider.ts

Q5: "You claim 9 alert channels — which are actually live?"

A: SMS (Twilio), Web Push (VAPID), Email (Nodemailer), FM Radio (5 strategies: CAP API, RDS, FTP, Email-to-studio, IVR), In-App, WhatsApp (webhook stub). All fan out in parallel from the alert engine. Twilio is bypassed in demo mode. FM strategies are implemented but need station APIs for end-to-end. lib/broadcast/fm-dispatcher.ts

Q6: "Is the RAG really using NDMA documents?"

A: The pipeline exists: PDF upload → text extraction → chunking → OpenAI embeddings (1536-dim) → pgvector HNSW index → cosine similarity search → context injection. If OPENAI_API_KEY is missing, it silently falls back to keyword search over stored chunks — no errors, no empty results. Demo uses seeded NDMA guideline chunks. lib/rag/

Q7: "How do you prevent a citizen from accessing the gov dashboard?"

A: Middleware enforces dual-mode crossover guards: a role=public cookie blocks /gov/* routes (redirects to /public/dashboard); a gov role blocks /public/* unless view_as_public is set. Admin routes require super_admin or district_admin — guests are bounced to 403. Three-layer enforcement: middleware + server actions + PostgreSQL RLS. middleware.ts

Q8: "What's the story with all those env vars — GLOFAS, NASA, Sentinel?"

A: Of ~40 env vars, only ~20 are wired into real code paths (Supabase, OpenWeatherMap, Groq/OpenRouter/Bluesminds, Twilio, VAPID, TTS providers). GLOFAS, NASA, Sentinel Hub, FIRMS, IMD, CWC, data.gov.in, GraphHopper, Novu, HDX are declared but not called anywhere. We do not claim live integration with them. .env.example

Q9: "Can this scale beyond Patna?"

A: Yes. The architecture is district-agnostic: PostGIS geospatial queries, pgvector RAG, CAP v1.2 radio, Dexie offline, LangGraph planning — all parameterized by district. Deploy to another district by seeding shelters, resources, FM stations, and alert rules. The middleware's district scoping and RLS policies handle isolation. prisma/schema.prisma lib/broadcast/auto-trigger.ts

Q10: "What's the biggest technical risk you're carrying?"

A: The ML model artifact is not checked in — the FastAPI service will fail to load it and return a mock label until train_model.py runs against historical_flood_data.csv. Also, the 6 MB JS chunk may slow cold start on stage Wi-Fi. Both are fixable before demo. ml_models/ next.config.mjs
